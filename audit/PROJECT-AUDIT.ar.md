# تقرير فحص NOKTA POS

تاريخ الفحص: 7 سبتمبر 2026. النطاق: نسخة المصدر في هذا المجلد، بإعداداتها ومكتباتها المثبتة وقت الفحص.

**النتيجة: توجد أعطال عالية الأولوية قد تفقد طلبات أو تغيّر مبالغ الفواتير أو تعطل الاستعادة. يجب إصلاح سلامة البيانات أولًا قبل الاعتماد التشغيلي على هذه النسخة.** لا يعني هذا أن فقدًا حدث في البيانات الفعلية؛ كل تجارب الكتابة نفذت على SQLite في الذاكرة.

## النطاق والدليل

- مراجعة جميع وحدات الخادم: 16 ملف مسارات، المصادقة، التدقيق، Socket.IO، مخطط قاعدة البيانات والترحيلات. مراجعة الواجهة الأساسية ومسارات الدخول والبيع والفواتير والمخزون والمطبخ والإغلاق والمزامنة، وإعدادات Electron وAndroid والبناء والتوثيق.
- فحص الصياغة لـ45 ملف JavaScript: 40 ملفًا في src وpublic/js وscripts، إضافة إلى server.js وelectron.js وpreload.js وpublic/sw.js وpublic/i18n.js. اجتازت الفحص؛ سلامة الصياغة لا تعني سلامة الوظائف.
- اختبار API حقيقي بخادم مؤقت على 127.0.0.1 وقاعدة بيانات `:memory:`، واختبارات محددة لمنطق الواجهة باستخدام بيئة DOM مبسطة. المصدر وبيانات العمل لم تُعدّل. أضيف مجلد audit فقط.
- يمكن إعادة إنتاج الدليل بواسطة `node audit/reproduce.cjs` من جذر المشروع. [نتائج التجربة](./results.json) و[سجلها](./run.log). الاختبار يثبت العيوب الحالية؛ نجاحه يعني إعادة إنتاجها، وليس اجتياز النظام لمتطلبات الجودة.
- لم يُنفذ اختبار شامل على Android أو Electron أو الطابعات الفعلية، ولا اختبار ضغط أو تحقق من كل شاشة بصريًا. لم تدقق ملفات SDK أو المكتبات التابعة كأنها كود المشروع، ولا محتوى بيانات العملاء أو كلمات المرور.
- فحص ثغرات الحزم غير مكتمل: أمر npm المحلي يشير إلى ملف مفقود، ومحاولة pnpm audit انتهت بـ `fetch failed`. لا توجد نتيجة موثوقة بعدد ثغرات التبعيات.

## إصلاحات عاجلة — P1

### 1. أوامر SQL تعطل الطاولات والمزامنة والإغلاق والمخزون

**مثبت بالتشغيل للطاولات والمزامنة، وبالكود لبقية المواضع.** `src/routes/orders.routes.js:142` يستخدم `status="occupied"`، و`src/routes/sync.routes.js:87` يستخدم `datetime("now")`. المكتبة المثبتة تفسر هذه القيم كأسماء أعمدة وتعيد 500. نفس النمط موجود في تحرير الطاولة وإضافة الطاولات وتعديل المخزون والإغلاق اليومي.

**الأثر:** طلب الطاولة يفشل بعد إدخال رأس الفاتورة، والمزامنة تفشل في نهايتها بعد احتمال حفظ طلبات بالفعل. **الإصلاح:** استخدام معاملات ربط للقيم أو اقتباس SQL المفرد، ومراجعة جميع المواضع ثم اختبار دورة طاولة ووردية ومخزون كاملة. [مرجع SQLite](https://www.sqlite.org/quirks.html#double_quoted_string_literals_are_accepted).

### 2. استعادة نسخة صادرة من النظام نفسه تفشل

**مثبت بالتشغيل.** `src/database/db.js:38–61` يعيد كائن المعاملات المسماة ثم يحاول نشره بـ `...safeParams`؛ الكائن ليس iterable. `src/routes/backup.routes.js:68` يمرر سجلات النسخة ككائنات، فتفشل الاستعادة بـ `Spread syntax requires ...iterable`.

**الإصلاح:** تمرير الكائن مباشرة إلى better-sqlite3، ونشر المصفوفات فقط. يشمل التصحيح run/get/all، ثم اختبار export → restore ومقارنة الحقول والسجلات.

### 3. فشل الاستعادة الكاملة يمكن أن يمسح بيانات موجودة

**مثبت بالتشغيل.** `src/routes/backup.routes.js:65–94`: معاملة الطلبات منفصلة، وحذف الأصناف والأقسام خارج معاملة شاملة. تجربة نسخة full تحتوي قائمة طلبات فارغة وصنف غير صالح انتهت بـ500، وبقي عدد الأصناف صفرًا بعد أن كان 15، والطلبات محذوفة.

**الإصلاح:** تحقق كامل من النسخة قبل الكتابة، ثم معاملة واحدة لكل الاستعادة، ونسخة أمان قابلة للرجوع. لا يكفي إصلاح نشر الكائنات في المشكلة السابقة.

### 4. المزامنة تمسح الطلبات المحلية عند رفض الخادم

**مثبت بمنطق الواجهة في بيئة معزولة.** `public/js/app.js:187–211` لا يفحص `syncRes.ok` ويمسح المخزن كله بعد قراءة JSON. اختُبرت استجابة 401 فاستُدعيت دالة المسح. استجابة 500 بصيغة JSON تسلك المسار نفسه. `public/sw.js:114–119` يمسح الجميع أيضًا عند استجابة ناجحة ولو نجح جزء من الدفعة فقط.

**الإصلاح:** حذف معرفات الطلبات المؤكد حفظها فقط، وإبقاء المرفوضة والجديدة، وانتظار اكتمال معاملة IndexedDB؛ عرض نجاح جزئي مع سبب رفض كل طلب. اختبار انتهاء الجلسة وفشل الشبكة وفشل بعض الطلبات.

### 5. إدخال الطلب ليس عملية واحدة متكاملة

**مثبت بالتشغيل.** `src/routes/orders.routes.js:110–174` يغير رقم الفاتورة ويدخل رأس الطلب قبل العناصر دون معاملة. خطأ في قيمة ملاحظة عنصر أعاد 500 وترك طلبًا إضافيًا محفوظًا. `src/routes/sync.routes.js:24–69` يعاني النمط نفسه؛ ويمكن أن يعامل الطلب الجزئي كمزامن في إعادة المحاولة بسبب offline_id.

**الإصلاح:** معاملة تجمع الرقم والرأس والعناصر والطاولة والمخزون والنقاط، ولا تُرسل الأحداث إلا بعد نجاحها. أضف معرف عملية ثابتًا لإعادة المحاولة وقيد تفرد مناسبًا، حتى لا يكرر الضغط أو إعادة الإرسال الفاتورة.

### 6. XSS مخزن في شاشة المطبخ ومواضع عرض أخرى

**مثبت وصول النص إلى HTML غير مهرب؛ لم ينفذ هجوم في متصفح فعلي.** `public/js/kds.js:197–223` يدخل ملاحظة العنصر واسم الصنف داخل innerHTML. الملاحظة يقبلها خادم الطلبات كما هي. الاختبار أظهر بقاء عنصر HTML ومعالج حدث داخله في ناتج العرض. أنماط مشابهة في المنيو والأسماء وسجل التدقيق ومعاينة النسخة.

**الأثر:** موظف يستطيع إدخال ملاحظة قد يشغّل JavaScript بصلاحيات جلسة من يعرضها، بما فيها جلسة مدير إذا عرضها. التخزين المحلي يحتوي token للمطبخ. **الإصلاح:** textContent للنصوص، وإنشاء عناصر DOM وربط الأحداث برمجيًا، والتحقق من روابط الصور؛ سياسة CSP مناسبة كطبقة إضافية بعد إزالة الأحداث المضمنة.

### 7. حساب الأوفلاين يختلف عن الحساب المباشر ويتغير بمجرد تعديل ملاحظة

**مثبت بالتشغيل.** `src/routes/sync.routes.js:38–63` يحسب إجماليًا لكنه لا يحفظ subtotal وdiscount_amount وtax_percent وtax_amount، ولا يضيف سعر الإضافات. تجربة بسعر 2 وكمية 2 وخصم مبلغ 1 وضريبة 10% حفظت 3.3، ثم تعديل الملاحظة فقط عبر PUT غيّر الإجمالي إلى 4. كان الطلب قد حُفظ رغم فشل استجابة المزامنة بسبب المشكلة 1.

**الإصلاح:** خدمة حساب موحدة بين الإنشاء والتعديل والمزامنة وإضافة عنصر، مع سياسة واضحة لأسعار الطلبات القديمة والأوفلاين، وحفظ تفاصيل السعر والضريبة والخصم. لا ترجع بيانات العميل غير المعتمدة للطباعة باعتبارها إجمالي الخادم.

### 8. حركة المخزون لا تطابق كل مسارات البيع

**مثبت جزئيًا بالتشغيل، والباقي بالكود.** إنشاء طلب completed مباشرة في `src/routes/orders.routes.js:91` لم يخصم المخزون: بقي 100 بدل 98. المزامنة أيضًا لا تخصم المخزون. التعديل يعكس ويعيد تطبيق المخزون خارج معاملة تعديل الطلب (`:269–310`)، وإضافة عنصر إلى فاتورة مكتملة (`:355`) تغير المبلغ دون تحديث المخزون والنقاط.

**الإصلاح:** توحيد تسجيل البيع والإلغاء والإرجاع ضمن معاملة واحدة، مع سجل حركة مرتبط بمعرف الطلب. تحديد الفرق بين حذف فاتورة وإرجاع بضاعة، واختبار إعادة إرسال العملية لمنع تكرار أثرها.

### 9. شاشة المخزون وإضافات الصنف لا ترسل المصادقة الصحيحة

**مثبت بالكود وباستجابة API.** `public/js/inventory.js:5,55,134` و`public/js/orders.js:127` تستخدم fetch دون Authorization؛ الخادم يطلبه ويرجع 401. حفظ المخزون وتعديله يستخدمان `getAuthHeaders()` في `inventory.js:79,115`، ولا يوجد تعريف لها في public.

**الإصلاح:** استخدام دالة api الموحدة، مع معالجة واضحة لـ401 و403 والأخطاء. اختبر القراءة والإضافة والتعديل بحساب مسموح وحساب ممنوع.

### 10. تعديل الفاتورة يستدعي مسارًا غير موجود

**مثبت بالكود وباستجابة 404.** `public/js/invoices.js:164–175` يحاول حذف العناصر عبر `/api/order-items/:id`، ولا يوجد هذا المسار في الخادم. تتوقف عملية حفظ التعديل عند أول عنصر قديم.

**الإصلاح:** إرسال العناصر النهائية مرة واحدة إلى PUT الطلب داخل معاملته، بعد إصلاح الحساب والمخزون؛ تجنب تفكيك تعديل الفاتورة إلى سلسلة حذف وإضافة منفصلة.

### 11. آخر حساب مدير يمكن تعطيله، فتُفتح تهيئة مدير جديد دون دخول

**مثبت بالتشغيل.** `src/routes/employees.routes.js:45` يسمح بتعطيل المدير نفسه عبر PUT، بينما `src/routes/auth.routes.js:45` يعتبر عدم وجود مدير نشط حالة تهيئة جديدة. بعد تعطيل المدير الوحيد، نجح POST غير مصادق إلى setup-admin وأنشأ مديرًا جديدًا بـ201.

**شرط الاستغلال:** تعطيل أو خفض رتبة آخر مدير مسبقًا؛ لا يعني أن إنشاء المدير مفتوح الآن مع وجود مدير نشط. **الإصلاح:** حالة تهيئة دائمة مستقلة، منع فقد آخر مدير نشط، واسترجاع إداري محلي مضبوط. كذلك مسار ترحيل PIN للمدير لا يشمله محدد المحاولات الموجود للدخول فقط.

### 12. صلاحية عرض الفواتير قابلة للتجاوز عبر مسار الطلبات

**مثبت بالتشغيل.** `src/routes/orders.routes.js:7,47,83` يطلب pos فقط، ويمكنه إرجاع الطلبات المكتملة لأي موظف، بل المحذوفة باستخدام not_deleted=0. حساب pos فقط مُنع من reports لكنه قرأ الفواتير المكتملة من orders رغم غياب view_invoices.

**الإصلاح:** السماح للـPOS بما يحتاجه من طلبات نشطة فقط، وتطبيق صلاحيات التاريخ والمحذوفات وحدود الموظف من الخادم في جميع المسارات البديلة. راجع أيضًا وصول أي حساب مصادق لقائمة العملاء الكاملة وإعدادات النظام حسب سياسة العمل.

## إصلاحات تالية — P2

### 13. العمل دون اتصال غير موصول بمسار الحفظ الحالي

**بالكود.** `saveOfflineOrder` معرف في `public/js/app.js:72` وليس له أي استدعاء في public. `saveOrder` في `public/js/orders.js:380–455` يحاول API ثم يعرض خطأ فقط. وجود مخزن وكاش وشريط أوفلاين لا يكفي لحفظ المبيعات عند انقطاع الخادم.

**الإصلاح:** توصيل حفظ الطلب بطابور دائم بمعرف ثابت وهوية الموظف، وإظهار حالة لم يُزامن، ثم تطبيق المزامنة الآمنة في المشكلة 4.

### 14. Service Worker لديه تعارض تخزين وإعداد شبكة غير مناسب للـPWA

**مثبت خطأ localStorage في بيئة worker، والبقية بالكود والوثائق.** `public/sw.js:133` يفتح IndexedDB الإصدار 1 بينما `public/js/app.js:60` يفتحه بالإصدار 2. كما يستخدم worker localStorage في `:161–175` وهي غير متاحة له. الملفات الأولية المخزنة دون query string تختلف عن روابط JS ذات الإصدارات في index، وبعض ملفات الشاشة غير موجودة في قائمة التهيئة.

الخادم وروابط Android تعتمد HTTP على الشبكة. Service Worker في المتصفحات الاعتيادية يحتاج سياقًا آمنًا؛ استثناء localhost لا يشمل عنوان LAN المعتاد. HTTP أيضًا ينقل الدخول وtoken دون تشفير. لم تُختبر أي طبقة HTTPS خارج هذا المشروع. **الإصلاح:** توحيد تخزين IndexedDB، بناء قائمة أصول صحيحة، وتهيئة HTTPS موثوقة للأجهزة. [مرجع MDN](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers).

### 15. قبول كميات عشرية ثم اقتطاعها عند الحساب

**مثبت بالتشغيل.** `src/routes/orders.routes.js:24` يستخدم parseInt، بينما تحقق الإنشاء يقبل 1.5. الاختبار حفظ كمية 1.5 لصنف سعره 2 لكن الإجمالي 2 بدل 3. **الإصلاح:** إما اشتراط كمية صحيحة للقطع، أو دعم كميات وزن بدقة موحدة دون parseInt في كل المسارات.

### 16. تحقق غير كافٍ من الخصم والدفع وانتقالات الحالة

**مثبت للخصم والإلغاء، والبقية بالكود.** الخصم -100 قُبل وضاعف الإجمالي. PUT يقبل قيم status دون قائمة وانتقالات مسموحة، ويقبل عناصر فارغة، ولا يتحقق من أن paid_amount يغطي المطلوب. موظف pos فقط يستطيع إلغاء طلبه عبر PUT دون delete_orders؛ يلزم تحديد هل هذا مقصود أم يتطلب صلاحية إلغاء مستقلة.

**الإصلاح:** مخطط تحقق موحد وحدود رقمية وإعدادات طرق الدفع المعتمدة، وصلاحيات صريحة للخصم والإلغاء والتعديل بعد الإغلاق. احسب الباقي في الخادم ولا تعتمد القيمة الواردة.

### 17. تعارض طلبات الطاولة قابل للظهور بعد إصلاح SQL

**ملاحظة كود؛ اختبار التعارض محجوب حاليًا بعطل SQL في المشكلة 1.** `src/routes/orders.routes.js:120–125` يفحص انشغال الطاولة ثم لا يتخذ إجراء. فتح طلب ثانٍ يستبدل current_order_id، وإنهاء الأول يفرغ الطاولة دون التأكد أن الربط يخصه (`:261–264`).

**الإصلاح:** سياسة واضحة لطلب واحد أو دمج طلبات، وقيد/تحقق داخل معاملة، وتحرير مشروط بمعرف الطلب الحالي. إعادة الاختبار بعد إصلاح SQL ضرورية.

### 18. النسخة «الكاملة» ناقصة حتى بعد إصلاح الاستعادة

**بالكود.** `src/routes/backup.routes.js:7–37` لا يصدر المخزون والحركات والإضافات وروابطها والورديات والإغلاق والتدقيق. يصدر الموظفين والطاولات لكن restore لا يعيدهما، ويسقط حقولًا مالية من الطلب مثل subtotal/tax_percent/tax_amount. استعادة orders فقط لا تضبط عداد الفواتير، ولا يوجد قيد تفرد على invoice_number.

**الإصلاح:** نسخة ذات إصدار ومخطط واضح تشمل البيانات المطلوبة للاسترجاع، أو تسمية التصدير بوضوح بأنه جزئي. اختبار الاستعادة في قاعدة جديدة ومقارنة العلاقات والعدادات، مع حماية بيانات الدخول ضمن آلية نسخ إدارية مناسبة.

### 19. اختلاف تعريف يوم البيع والوردية

**بالكود.** `src/routes/reports.routes.js:19` يعتمد completed_at، بينما التقرير اليومي `:51` يعتمد created_at. طلب فُتح قبل منتصف الليل ودُفع بعده يظهر في يومين مختلفين بحسب التقرير. بعض الواجهات تختار التاريخ المحلي بينما SQLite تخزن UTC. `src/routes/shifts.routes.js:51` يحسب بتاريخ الإنشاء دون حد نهاية ولا استخدام shift_id، ومسار الإغلاق لا يمنع إعادة إغلاق وردية مغلقة.

**الإصلاح:** منطقة زمنية ويوم عمل محددان للمنشأة، نطاق UTC واضح لكل يوم، ربط البيع بالوردية المناسبة، ومنع إعادة كتابة الإغلاق إلا بإجراء تدقيقي مصرح.

### 20. تعليم الطلب جاهزًا في المطبخ قد يعيد تسعيره أو يكتب فوق تعديل أحدث

**بالكود.** `public/js/kds.js:140–159` يجلب الطلب ثم يعيد إرسال كل العناصر والحالة لتغيير attributes فقط. الخادم يعيد قراءة السعر الحالي للصنف في PUT؛ تحديث السعر بين البيع والتجهيز قد يغير الحساب. تغيير آخر من الكاشير بين GET وPUT قد يُستبدل.

**الإصلاح:** مسار مخصص لحالة التجهيز، صلاحية مطبخ محدودة، ورقم إصدار لمنع الكتابة فوق تعديلات أحدث. لا تمنح تحريرًا ماليًا شاملًا للمطبخ فقط لتمكين زر جاهز.

### 21. Socket.IO لا يطبق صلاحيات الموظف الحالية

**بالكود.** `src/socket/socket.handler.js:7` يتحقق من توقيع token وانتهائه فقط عند الاتصال؛ لا يتحقق من وجود موظف نشط أو صلاحياته. `:15` يبث الأحداث للجميع. موظف عُطل حسابه قد يعيد الاتصال برمز لم ينتهِ، والاتصالات الحالية لا تُلغى بتغيير الصلاحيات.

**الإصلاح:** جلب المستخدم النشط والتحقق من الصلاحيات، تقسيم الأحداث حسب الحاجة، وإبطال/قطع الجلسات عند تعطيل الحساب أو تغيير بيانات الدخول. لا توجد تجربة اتصال Socket فعلية ضمن هذا الفحص.

### 22. سجلات المخزون ومسارات API المفقودة تتخفى كصفحة HTML ناجحة

**مثبت بالتشغيل.** `public/js/inventory.js:134` يطلب `/api/inventory/:id/logs` دون وجود المسار. `src/app.js:98` يعيد index.html برمز 200 لمسار GET المفقود؛ ثم يفشل parsing في الواجهة. **الإصلاح:** إضافة المسار وصلاحيته، وإرجاع JSON 404 لجميع مسارات /api غير الموجودة قبل fallback الواجهة.

## قابلية الصيانة والتشغيل — P3

- لا يوجد أمر test أو lint في package.json، وcheck.js يحاول قراءة public/app.js غير الموجود. ملفات Android الاختبارية قوالب عامة. أضف اختبارات دورة البيع والاستعادة والأوفلاين والصلاحيات أولًا.
- package-lock.json لا يطابق package.json في تبعيات Capacitor، بينما pnpm-lock.yaml يتضمنها. اختيار مدير حزم واحد وتثبيت إصدار Node وخطوات بناء قابلة للتكرار يقلل اختلاف الأجهزة، خصوصًا مع better-sqlite3 وElectron.
- لا يوجد مستودع Git في المجلد وقت الفحص. PROJECT-HANDOFF.md وPROJECT-SPEC.md ما زالا يصفان sql.js والحفظ الدوري رغم انتقال المصدر إلى better-sqlite3. حدّث التوثيق وأضف تحكمًا بالإصدارات قبل الإصلاحات الكبيرة.
- مخطط SQLite يفتقد روابط FOREIGN KEY وقيود CHECK وتفرد offline_id؛ بعض المسارات تقبل معرفات غير موجودة. أضف القيود بعد فحص وتنظيف البيانات القديمة، لا بتطبيق ترحيل أعمى.
- قوائم الطلبات غير محدودة، وwith_items يبني معاملًا لكل طلب؛ سجلات التدقيق وبعض LIMIT تقبل حدودًا غير منضبطة. يلزم ترقيم صفحات وحد أعلى واختبار حجم واقعي.
- سجلات الدخول وتغيير الموظف موجودة، لكن تدقيق إنشاء الطلب يسجل total القادم من العميل (`orders.routes.js:177`) بدل الإجمالي المحسوب. فشل التدقيق يُبتلع، وبعض تغييرات العملاء والمخزون بلا سجل تدقيق إداري موحد.
- تكرار PIN لموظفين مختلفين غير ممنوع؛ دخول PIN يختار أول تطابق. لا توجد سياسة إبطال token عند تغيير كلمة المرور. يلزم اختبار دورة حياة حساب الموظف ومنع التباس الهوية.
- Chart.js يُحمّل من CDN دون إصدار محدد، وملفات صوت وخطوط تعتمد الإنترنت. استضافة الأصول اللازمة محليًا تجعل عمل الشبكة الداخلية أكثر قابلية للتوقع.
